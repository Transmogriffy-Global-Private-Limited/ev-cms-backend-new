# CPO Administration API

For exhaustive headers, schemas, errors, state effects, and client sequencing,
use `docs/contracts/api/administrative-http-api.md`. The same operations are
executable from the embedded Swagger UI at `/docs/`.

## Boundary

Base path: `/api/v1/platform/cpos`

Every endpoint requires an authenticated `PLATFORM` session:

```http
Authorization: Bearer <encrypted-platform-access-token>
```

`X-CPO-App-ID` is deliberately not required on this control-plane API. CPO
creation and lifecycle have no subscription dependency. The app ID is
application-routing metadata, not a credential.

## Create a CPO and Initial Administrator

`POST /api/v1/platform/cpos`

```json
{
  "slug": "example-charging",
  "business_name": "Example Charging Private Limited",
  "company_type": "COMPANY",
  "gstin": "19ABCDE1234F1Z5",
  "address": "1 Example Road",
  "city": "Kolkata",
  "state": "West Bengal",
  "pincode": "700001",
  "admin": {
    "email": "admin@example.com",
    "full_name": "CPO Administrator"
  }
}
```

Successful status: `201 Created`.

```json
{
  "cpo": {
    "id": "c821a013-5041-42f7-80c8-aa153cf9d455",
    "slug": "example-charging",
    "business_name": "Example Charging Private Limited",
    "company_type": "COMPANY",
    "gstin": "19ABCDE1234F1Z5",
    "address": "1 Example Road",
    "city": "Kolkata",
    "state": "West Bengal",
    "pincode": "700001",
    "status": "PENDING",
    "app_id": "cpo_dummy_735f36a898b84ce68a350db38c90bf9b",
    "app_id_mode": "DUMMY",
    "app_id_updated_at": "2026-07-23T12:00:00Z",
    "created_at": "2026-07-23T12:00:00Z",
    "updated_at": "2026-07-23T12:00:00Z"
  },
  "admin": {
    "user_id": "5cef4c95-a1da-448e-bd7c-19d570cd4497",
    "email": "admin@example.com",
    "full_name": "CPO Administrator",
    "role": "ADMIN",
    "identity_created": true
  }
}
```

The server owns `status`, `app_id`, and `app_id_mode`; clients cannot submit
them.

Creation commits the CPO, first `ADMIN` membership, audit record, and encrypted
mail job in one transaction:

- New email: create an identity with an Argon2id-hashed autogenerated temporary
  password and `must_change_password=true`. The welcome email contains CPO ID,
  dummy app ID, and the temporary password. The API never returns the password.
- Existing active email: preserve its identity and password, add the
  membership, and email the CPO ID and app ID without a password.
- Inactive existing email: reject with `409 admin_identity_inactive`.
- Mail disabled: reject with `503 mail_unavailable` before creating anything.

Concurrent creation requests using the same new administrator email are
serialized so exactly one global identity is created and each CPO receives its
own membership.

The CPO begins `PENDING`. It cannot be used for CPO login until a platform
superadmin activates it.

## List and Inspect

- `GET /api/v1/platform/cpos` returns `{"cpos": [...]}` for at most the 100
  newest CPOs.
- `GET /api/v1/platform/cpos/{cpo_id}` returns one CPO.

No subscription record is read or returned.

## Activate and Suspend

- `POST /api/v1/platform/cpos/{cpo_id}/activate`
- `POST /api/v1/platform/cpos/{cpo_id}/suspend`

Both return the updated CPO and are idempotent for their requested state.
Activation permits CPO login with either a dummy or live app ID. Suspension
blocks new CPO login and invalidates current CPO sessions and refresh tokens.
Neither operation creates or checks a subscription.

## Assign or Rotate the Live App ID

`PUT /api/v1/platform/cpos/{cpo_id}/app-id`

```json
{
  "app_id": "example_charging_production"
}
```

The value is normalized to lowercase and must contain 16 to 100 lowercase
letters, digits, underscores, or hyphens. The reserved `cpo_dummy_` prefix is
not accepted. App IDs are globally unique.

The response returns the CPO with `app_id_mode: "LIVE"`. Rotation takes effect
immediately: existing access sessions remain valid, authentication recovery
endpoints expose the current ID, and tenant business APIs reject the previous
header value.

## CPO Request Contract

After CPO login, verification and refresh responses return:

```json
{
  "cpo_app_id": "cpo_dummy_735f36a898b84ce68a350db38c90bf9b",
  "cpo_app_id_mode": "DUMMY",
  "must_change_password": true
}
```

`GET /api/v1/auth/me` returns the same current app identity. Every implemented
CPO business API requires:

```http
Authorization: Bearer <encrypted-cpo-access-token>
X-CPO-App-ID: <current-cpo-app-id>
```

Validation first establishes the CPO from the authenticated session, then
compares the header with that CPO's current ID. The header never selects a CPO
or grants authority. Missing headers return `missing_cpo_app_id`; mismatches
return `cpo_app_id_mismatch`.

Health, `/api/v1/auth/*`, and `/api/v1/platform/*` are exempt to prevent login,
recovery, password-change, session-control, and app-ID-rotation deadlocks.
Customer/app-user and future independently authenticated callback surfaces
must apply the equivalent boundary appropriate to their own authentication
model.

## First-Login Password Rule

The autogenerated password has no hard expiry. After every successful login
while it remains unchanged, the service queues an encrypted
`PASSWORD_CHANGE_REMINDER` email.

Authentication, password recovery/change, logout, and session APIs stay
available. Tenant business APIs return `password_change_required` until
`POST /api/v1/auth/password/change` or password reset clears the flag. Either
operation revokes all existing sessions, so the administrator signs in again.
